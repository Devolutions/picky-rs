# picky-crypto-testsuite

## Purpose

Independent conformance suite for the `picky-crypto` contract.

Its expectations are derived from the contract specification and from published standards, treating every backend as a black box.
It is the executable form of the contract: a backend is correct when it passes this suite.

## Invariants

- Among cryptographic crates, it depends only on the contract crate: no backend and no cryptography library.
  Generic test tooling (data parsing, property testing) is allowed.
  That dependency direction enforces mechanically that it has no knowledge of the implementation.
- Test vectors come only from published sources (Wycheproof, NIST CAVP), with citations.
  Never let an agent invent vectors, because LLMs can't compute SHA-256 and will produce plausible-looking wrong values.
- Derived test inputs are allowed only for properties that published sources do not cover.
  They are built from cited published inputs by swapping or substituting whole encoded fields between cited inputs, without arithmetic or generated bytes.
  Their expected outcome is a property stated by the contract, never a computed value.
  Each derivation has a control: reassembling the unmodified fields reproduces the cited bytes exactly.
- Published inputs may be re-encoded into the contract's encodings by test-only format code (fixed constants, DER length and sign octets, fixed-width padding).
  The expected outcome stays the published one, and the encoder must reproduce the published bytes of every source that gives both forms.
  Every re-encoded key is also used by at least one published vector that expects success, so an encoding error can't make failure vectors pass vacuously.
- A vector is an input paired with a computed expected output.
  Literal structural inputs whose expected outcome is a specified error (empty, zero, one, lengths at or beyond a limit) are not vectors and may be written by hand.
  A hand-written input never expects success.

## Required behavior

The suite exposes each conformance area as a function over a provider; the `picky-crypto-conformance` runner calls every area for every backend provider and composition the workspace ships.

The suite verifies, for every algorithm a provider advertises:

- known-answer tests from published vectors;
- round trips where applicable (sign then verify, encrypt then decrypt, key agreement on both sides);
- algorithms with non-deterministic output (for example ECDSA) are checked through verification, never by comparing outputs;
- malformed inputs (wrong key sizes, truncated signatures, invalid encodings) produce errors, never panics;
- verification failures carry no reason.

For every algorithm a provider does not advertise, the suite verifies that the operation returns `Unsupported`.

Differential areas take two providers and compare them (for example, sign with one and verify with the other); the runner calls them for every pair of providers in a build.

## Authority

A test failing against a backend is resolved by fixing the backend.
If the test itself appears wrong, the discrepancy is escalated to a human with evidence from the cited source.
Tests are never weakened to make a backend pass.
